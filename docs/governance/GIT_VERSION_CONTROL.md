# Git 与 GitHub 版本控制准则

> 文档级别：`LOCKED`  
> 修改权限：仅当用户在当前任务中明确点名本文件，或明确授权改变 Git、GitHub、提交、推送、分支、标签或历史保护规则时可改；本次授权不延续到未来。  
> 适用版本：`1.1.0` 起，直至用户明确替换。  
> 最后核对日期：`2026-08-15`  
> 权威来源：用户明确决策；根目录 `AGENTS.md`；`docs/governance/DOCUMENT_CONTROL.md`；仓库当前 Git 配置与 GitHub 远端。  
> 更新触发：用户明确改变强制版本管理、远端仓库、默认分支、提交与推送闭环、历史保护或正式版本标签策略时。

## 1. 强制适用范围

- 所有代理对仓库中的源码、配置、测试、脚本、素材或 Markdown 产生可跟踪文件变更时，都必须使用 Git 记录版本，并把完成且通过相应验证的提交上传到 GitHub。
- 文件变更任务只有在“检查差异、完成验证、建立有意提交、推送远端并核对结果”全部完成后，才可以报告为完整交付。
- 只读审查、解释、状态查询或没有产生可跟踪差异的任务不创建空提交，也不需要推送。
- 被 `.gitignore` 正确排除的依赖、构建缓存、安装包和临时文件不进入源码提交；任务只产生这类文件时，应如实报告没有可提交差异。
- 用户在当前任务中的明确指示可以要求暂不提交或暂不推送；代理必须把它作为本次例外明确报告，不得把一次例外扩展到未来任务。

## 2. 权威仓库身份

| 项目 | 固定值 |
| --- | --- |
| GitHub 仓库 | `RizardSKs/little-orange-desktop-pet` |
| `origin` | `https://github.com/RizardSKs/little-orange-desktop-pet.git` |
| 默认分支 | `main` |

不得擅自删除、替换或改指向 `origin`，不得把项目推送到其他个人或组织仓库。迁移仓库、改变默认分支或调整远端所有权必须获得用户在当前任务中的明确授权。

## 3. 开始任务前的 Git 检查

产生文件变更前至少核对：

```powershell
git status -sb
git branch --show-current
git remote -v
```

- 必须识别当前分支、跟踪分支、远端地址以及已有未提交或未推送内容。
- 发现与当前任务无关的改动时必须保留；只暂存本任务文件，不得用批量暂存把来源不明的内容混入提交。
- 若当前任务需要修改的文件与已有改动重叠，且无法安全区分归属，必须停止编辑并向用户确认。
- 可以获取远端状态并比较领先或落后情况，但不得在未审查影响时自动合并、变基或覆盖本地内容。

## 4. 验证与提交

提交前必须：

1. 审查本任务的工作区差异和暂存差异，确认范围最小且不包含凭据、秘密或无关文件。
2. 按 `AGENTS.md` 和[测试与验收](../reference/TESTING_AND_ACCEPTANCE.md)运行与变更风险相称的检查。
3. 运行 `git diff --cached --check`；若存在有意的格式例外，应通过明确、最小的仓库规则处理，不得静默忽略未知错误。
4. 使用能准确描述结果的提交信息；一个提交只承载一个清晰、可回退的逻辑变更，不创建空提交。

工作区混有其他改动时应显式暂存目标路径。只有在已经确认整个工作区全部属于当前任务时，才可使用 `git add --all`。

测试或构建失败时不得把任务描述为完成，也不得默认推送失败状态。若用户明确要求保存诊断或阶段性工作，必须使用清楚的未完成说明，并在交付中列出失败检查。

## 5. 上传 GitHub 与结果核对

- 完成提交后必须推送当前任务分支。已有上游分支时使用普通 `git push`；没有上游时使用 `git push -u origin <branch>`。
- 若当前分支受保护、直接推送被拒绝或任务明确要求评审，应使用独立任务分支上传，并按用户要求建立 Pull Request；不得绕过保护规则。
- 推送后必须核对本地分支与远端一致，并确认目标提交确实存在于 GitHub；仅看到本地提交不算上传成功。
- 交付说明必须包含分支、提交哈希、推送结果、已运行检查和最终工作区状态。
- 网络、凭据、权限或 GitHub 服务异常导致无法推送时，应保留已经验证的本地提交并报告阻塞原因；不得声称已上传，不得把令牌或凭据写入命令、项目文件或日志。

## 6. 历史与敏感内容保护

- 未经用户在当前任务中明确授权，禁止使用 `--force` 或 `--force-with-lease` 强制推送，禁止改写已发布提交、变基已共享历史、修改已推送提交、删除远端分支或删除、移动、复用已发布标签。
- 禁止使用 `git reset --hard`、`git clean`、覆盖检出或其他方式丢弃用户改动，除非用户明确指定准确目标并授权该破坏性操作。
- `.env`、访问令牌、密码、私钥、签名证书和其他凭据不得进入 Git 历史；发现疑似秘密时必须停止提交并报告。
- `node_modules/`、`dist/`、`dist-electron/`、`release/`、`coverage/`、日志和临时目录保持排除。正式安装包通过受控发行渠道交付，不放入源码历史。

## 7. 版本标签与正式发布

- 普通文件变更的 GitHub 闭环只要求推送任务分支；不得因此自动创建或移动版本标签、创建 GitHub Release、上传 Setup/Update 或其他安装包。
- 只有用户明确发起正式发布，并且[发布与兼容性准则](RELEASE_AND_COMPATIBILITY.md)的门槛全部通过后，才可以执行版本标签、GitHub Release 和发行物上传操作。
- `vX.Y.Z` 标签只用于已经完成[发布与兼容性准则](RELEASE_AND_COMPATIBILITY.md)所规定验证的正式版本，不为普通开发提交随意打版本标签。
- 正式版本标签必须与 `package.json`、`package-lock.json`、`CHANGELOG.md` 和对应发布快照的版本一致，并指向实际用于生成发行物的提交。
- 已推送的正式版本标签只追加、不移动、不复用。发现历史错误时追加勘误或发布新的修正版本，不改写旧标签所指历史。

## 8. 无法完成闭环时

以下任一情况都必须如实报告，不能把任务标记为已经完整上传：

- 无法确认改动归属或暂存范围。
- 必需检查失败或没有条件运行。
- GitHub 远端不可访问、身份验证失败或没有推送权限。
- 本地与远端历史发生分歧，安全解决方式需要用户选择。
- 请求需要破坏或改写已发布历史，但当前任务没有明确授权。
