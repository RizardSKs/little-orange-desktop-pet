# 文档控制规则

> 文档级别：`LOCKED`  
> 修改权限：仅当用户在当前任务中明确点名本文件或明确授权变更文档控制规则时可改；本次创建授权不延续到未来，普通“更新文档”不构成授权。  
> 适用版本：`1.1.0` 起，直至用户明确替换。  
> 最后核对日期：`2026-08-15`  
> 权威来源：用户明确决策；根目录 `AGENTS.md`；本目录受保护治理文档。  
> 更新触发：用户明确调整文档分类、保护范围、授权方式、权威顺序或版本记录规则时。

## 1. 文档分类

项目文档必须明确归入以下一种类型：

| 级别 | 用途 | 允许的常规操作 |
| --- | --- | --- |
| `LOCKED` | 长期治理、产品底线、安全边界和发布兼容承诺 | 未获当前任务的明确授权时只读 |
| `LIVING` | 当前架构、变量、功能规则、接口、素材和测试参考 | 与相关代码在同一任务中同步更新 |
| `APPEND_ONLY` | 更新日志、发布记录、决策历史 | 可追加新记录，不得擅自改写或删除旧记录 |

正式版本快照在发布后按 `APPEND_ONLY` 管理；发现错误时追加勘误，不覆盖当时记录。

## 2. 必需控制信息

每份开发文档开头必须包含：

- 文档级别。
- 修改权限。
- 适用版本。
- 最后核对日期。
- 权威来源，包括对应源码、配置、测试或用户决策。
- 更新触发，说明什么变化要求同步该文档。

新建文件使用英文大写加下划线命名，例如 `GROWTH_AND_EXPERIENCE.md`；正文使用中文，代码符号、字段名和命令保持原文。

## 3. 受保护文件

以下文件为完整受保护清单：

- `AGENTS.md`
- `docs/governance/DOCUMENT_CONTROL.md`
- `docs/governance/PRODUCT_GUARDRAILS.md`
- `docs/governance/RELEASE_AND_COMPATIBILITY.md`
- `docs/governance/ARCHITECTURE_SECURITY.md`
- `docs/governance/GIT_VERSION_CONTROL.md`

新增 `LOCKED` 文档时，必须同时在本清单和根目录 `AGENTS.md` 中登记；因为这会修改受保护文件，所以必须获得用户明确授权。

## 4. 授权判定

- 有效授权必须发生在当前任务中，并明确点名要修改的受保护文件，或明确点名要改变的受保护规则及涉及文件。
- “更新文档”“同步说明”“整理 Markdown”“把文档改好”等笼统请求，不构成修改 `LOCKED` 文档的授权。
- 一次授权只覆盖该任务明示的修改，不会传递到后续任务、子任务或未来代理。
- 本文档及其他治理文档的首次创建授权在本次任务结束后失效，不得作为未来修改依据。
- 未获授权时可以只读审查、报告漂移并提出修改建议，但不得直接改动受保护文件。

## 5. 权威来源与冲突处理

- 用户明确决策和 `LOCKED` 文档定义目标与禁止事项。
- 源码、配置和自动化测试定义当前实现事实。
- `LIVING` 文档解释当前实现，必须引用真实路径和符号，并随实现同步。
- `APPEND_ONLY` 文档记录历史，不应被当作当前实现的唯一依据。

若源码与治理规则冲突，必须记录为“实现偏离治理规则”，停止相关扩大修改并请求用户决定；禁止把治理文档改成与代码一致来掩盖偏离。若 `LIVING` 文档与代码冲突，在任务授权范围内以代码事实修正文档，并说明差异。

## 6. 变更闭环

每个行为或接口变更必须完成以下闭环：

1. 定位对应实现、测试和权威参考文档。
2. 以最小差异修改实现。
3. 新增或更新测试并运行相关检查。
4. 同步对应 `LIVING` 文档中的参数、流程、边界和源码引用。
5. 对用户可见变化追加更新日志；发布时追加版本快照和实测结果。
6. 按 [Git 与 GitHub 版本控制准则](GIT_VERSION_CONTROL.md)建立有意提交、推送 GitHub 并核对远端结果。

文档中的数值表不得重复充当多个权威来源。配置登记表记录变量，领域文档解释变量如何参与规则并链接到登记表。
